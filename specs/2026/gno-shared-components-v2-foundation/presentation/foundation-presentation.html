GNO shared components

A reusable foundation for GNO portal interfaces.

Team-lead presentation · 2026-10-08 · Foundation review

01 · Purpose

One package for GNO portal products

Create configurable, reusable components that separate GNO UI contracts from individual applications while supporting JavaScript and TypeScript consumers.

Reusable

Install once, import approved named components.

Configurable

Consumer-owned routes, data, branding, and integrations.

GNO-focused

Designed for composed portal UI, not generic starter components.

02 · Foundation

What is already established

  • npm workspace and publishable packages/ui package
  • JavaScript runtime output with TypeScript declarations
  • Shared CSS/token foundation
  • Next.js showcase and consumer catalog
  • Storybook, Vitest, accessibility checks, and CI
  • GNO-specific documentation and GitHub origin

03 · Technical architecture

Package-first boundaries for real consumer applications

Consumer Next.js / JavaScript application
        │ npm install + named imports
        ▼
gno-shared-components (published workspace package)
        ├─ dist/index.js       ESM runtime
        ├─ dist/index.d.ts     Type declarations
        └─ dist/styles.css     Explicit CSS contract
        │ React peer dependency
        ▼
Component modules
        ├─ framework-neutral React UI
        ├─ component-scoped tokens and styles
        └─ optional approved framework adapters

Package boundary

packages/ui is the only publishable artifact. The root orchestrates the showcase and tooling.

Runtime boundary

React is a peer dependency. Components are server-compatible by default; client boundaries stay narrow.

Style boundary

Consumers explicitly import compiled CSS and do not need to scan package source with Tailwind.

Storybook boundary

Every approved component owns a story for its API, states, controls, responsive behavior, and interactions.

npm ci → typecheck/lint/test → package build → Storybook build
      → Next.js production build → npm pack --dry-run

Next.js consumer

// app/layout.tsx
import { PortalHeader, PortalFooter } from "gno-shared-components";
import "gno-shared-components/styles.css";

export default function Layout({ children }) {
  return <>
    <PortalHeader navigation={navigation} />
    {children}
    <PortalFooter links={[{ label: "Contact", href: "/contact" }]} />
  </>;
}

React JavaScript consumer

import { createRoot } from "react-dom/client";
import { PortalHeader, PortalFooter } from "gno-shared-components";
import "gno-shared-components/styles.css";

createRoot(document.getElementById("root"))
  .render(<>
    <PortalHeader navigation={navigation} />
    <PortalFooter links={[{ label: "Contact", href: "/contact" }]} />
  </>);

The Bitbucket URL is the release source; the installed package and import name remain gno-shared-components. The package is designed for both JavaScript and TypeScript repositories.

Illustrative APIs pending approval: consumers compose approved components and provide application data; each component owns its layout, responsive behavior, accessibility, and scoped styles.

Implementation model

Next.js consumers render <PortalHeader /> in a page or layout. Other React JavaScript consumers render it through their existing React root. The foundation does not expose a raw <portal-header> custom element; that adapter would require separate approval.

Consumer setup

Install the approved version, import a named export, and import the package stylesheet once at the application style boundary.

Component guidance

Use /catalog for props, states, accessibility, responsive behavior, and the linked Storybook story.

Ownership

The application owns routes, data, authentication, and integrations. The package owns the component contract, styles, tests, and story.

10 · Versioning

One package version, predictable component releases

Start with one semantic version for the entire package. A component change determines the package bump.

ChangeVersion impactExample
New component or backward-compatible featureMinor0.1.0 → 0.2.0
Bug, accessibility, or non-breaking style fixPatch0.2.0 → 0.2.1
Removed export, renamed prop, breaking token/API changeMajor0.2.1 → 1.0.0
PortalHeader pre-release validationPre-release0.3.0-rc.1

Every release requires a changelog entry, package dry-run, validation evidence, and migration notes for breaking changes. Independent component versions can be introduced later only if release cadence or dependency boundaries justify them.

annotated Git tag v0.1.0 → Bitbucket pipeline → build and validate
                         → gno-shared-components-0.1.0.tgz
                         → Bitbucket Downloads/release artifact

Consumers install the versioned .tgz; Git tags preserve package release history.
